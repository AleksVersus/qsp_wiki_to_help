# Сборка справки QSP

Проект `qsp_help_builder` собирает справку из `wiki.qsp.org` в несколько форматов, а также позволяет отдельно собирать выходные форматы из Markdown-источников Docusaurus.

Все рабочие пути и параметры задаются в `qsp_help.toml`. Текущая директория запуска не влияет на результат: конфигурация ищется в корне проекта, рядом с пакетом. Если конфигурация расположена нестандартно, укажите её явно через `--config <путь>`.

## Подготовка

### 1. Установите зависимости

```bash
pip install -r requirements.txt
```

В проекте используются `requests`, `beautifulsoup4`, `lxml`, `markdown-it-py`, `mdit-py-plugins` и `PyYAML`.

### 2. Проверьте конфигурацию

Настройки сборки находятся в `qsp_help.toml`. Файл обязателен: встроенных значений по умолчанию в коде нет.

В конфигурации задаются рабочие каталоги, страницы запуска, ресурсы, base URL, кодировки, исключаемые разделы и уровень логирования. Параметры конкретного формата описаны в соответствующих секциях конфигурации.

### 3. Как запускать команды

Команды выполняются из корня проекта:

```bash
python -m qsp_help_builder <команда>
```

При необходимости путь к конфигурации можно передать параметром `--config <путь>`.

## Общие сведения

### Основные команды

| Команда | Назначение |
|---|---|
| `download` | Скачать страницы и изображения с wiki.qsp.org в `.build/wiki` |
| `prepare` | Подготовить корпус wiki для CHM: HTML-файлы, `qsp.hhc`, `qsp.hhk` |
| `anchors` | Извлечь якоря из подготовленного CHM-каталога и сохранить в `anchors.json` |
| `all` | Выполнить `download` → `prepare` → `anchors` |
| `spa` | Собрать автономный одностраничник из `.build/wiki` |
| `pwa` | Собрать PWA для размещения на веб-сервере из `.build/wiki` |
| `docusaurus` | Преобразовать корпус wiki в дерево Markdown для Docusaurus |
|---|---|
| `markdown-sync` | Синхронизировать Markdown-источники Docusaurus |
| `markdown-validate` | Проверить синхронизированные Markdown-источники |
| `markdown-build --target …` | Собрать CHM, SPA или PWA из Markdown-источников |

### Общий исходник wiki

Все wiki-сценарии используют один скачанный корпус:

```text
.build/wiki/
```

Содержимое этого каталога готовит команда `download`. Повторное скачивание полностью перезаписывает корпус. Вики использует изменяющиеся per-request токены (`sec`/`tok`/`rev`), поэтому байты файлов могут отличаться после каждого скачивания — это ожидаемое поведение.

Скачанные страницы и изображения сохраняются в `.build/wiki`; изображения — в `.build/wiki/images`. Там же создаётся `urls_links_to_files.json`, связывающий прямые URL и локальные файлы. Имена скачанных изображений определяются значением `media` (например, `namespace:file` преобразуется в `namespace_file`), а не общим именем `fetch.png`.

Для повторного получения исходников достаточно снова выполнить `download`.

### Ресурсы и оформление

Статические ресурсы находятся в `assets/` и копируются в выходные каталоги во время сборки.

- `assets/chm` — ресурсы CHM (ключ `[chm].res`).
- `assets/spa` — ресурсы SPA и PWA (ключ `[spa].res`).

CSS для CHM и одностраничника различается. Docusaurus оформляет сайт самостоятельно, поэтому внешний вид его дерева не задаётся ресурсами сборщика.

В PWA wiki-root-absolute пути `url()` в CSS (например, `/lib/…`, декоративные иконки DokuWiki, которых нет в локальном корпусе) переписываются на URL оригинальной wiki. Эти элементы могут загружаться онлайн и исчезать офлайн; основной контент при этом остаётся доступным.

## wiki.qsp.org → CHM

Получение CHM состоит из подготовки файлов сборщиком и последующей компиляции внешней программой HTML Help Workshop.

### Шаг 1. Скачать wiki

Если корпус `.build/wiki` ещё не скачан или его нужно обновить, выполните [общие действия по загрузке](#общий-исходник-wiki):

```bash
python -m qsp_help_builder download
```

### Шаг 2. Подготовить файлы CHM

```bash
python -m qsp_help_builder prepare
```

Команда использует `.build/wiki` и создаёт подготовленные страницы в:

```text
.build/chm/
```

В каталоге формируются HTML-страницы, `qsp.hhc` (содержание) и `qsp.hhk` (указатель). Страницы сохраняются в UTF-8, файлы содержания и указателя — в Windows-1251, как требуется HTML Help Workshop.

В процессе подготовки автоматически выполняются:

- исключение разделов, заданных в конфигурации (в том числе навигатор и aqsp);
- очистка ссылок и изображений;
- снятие кликабельности с изображений;
- удаление изображений-иконок;
- правка стартовой страницы;
- добавление лога и ссылки на живую wiki;
- автоматическая генерация `qsp.hhk` на основе таблицы `help_keywords` и актуальных якорей из `.build/wiki/anchors.json`;
- вставка сохранённых якорей из `.build/wiki/anchors.json`.

Статические ресурсы копируются из `assets/`. Другие изображения, необходимые в CHM (например, `qgen.png`), сборщик автоматически не копирует — их следует разместить вручную.

### Шаг 3. Обновить якоря

После подготовки можно извлечь актуальные якоря из CHM-каталога:

```bash
python -m qsp_help_builder anchors
```

Якоря сохраняются в `.build/wiki/anchors.json` и используются при следующей подготовке. Цикл `prepare` → `anchors` замкнут; после обновления wiki система обычно сходится к стабильному состоянию за 2–3 итерации.

### Шаг 4. Скомпилировать CHM

1. Установите HTML Help Workshop. Установщик и инструкция находятся в `tools/html_help_workshop`.
2. Создайте проект в HTML Help Workshop.
3. Добавьте подготовленные файлы из `.build/chm`.
4. Укажите нужную стартовую страницу (`Default file`).
5. Запустите компиляцию и проверьте сообщения об ошибках.

Компиляция `.chm` самим `qsp_help_builder` не выполняется.

### Короткий вариант повторной сборки

Если скачивание и подготовка должны быть выполнены заново, можно использовать:

```bash
python -m qsp_help_builder all
```

Эта команда выполняет `download` → `prepare` → `anchors`. После этого остаётся скомпилировать CHM в HTML Help Workshop.

## wiki.qsp.org → SPA

SPA — автономный одностраничник, который можно открыть локально без веб-сервера.

### Шаг 1. Скачать wiki

Если `.build/wiki` отсутствует или нужно обновить исходники, выполните [общие действия по загрузке](#общий-исходник-wiki):

```bash
python -m qsp_help_builder download
```

### Шаг 2. Собрать SPA

```bash
python -m qsp_help_builder spa
```

Результат по умолчанию:

```text
.build/spa/
├── index.html
└── images/
```

Каталог результата задаётся параметром `[spa].out` в `qsp_help.toml`, стартовая страница — `[spa].start_page`.

SPA содержит hash-навигацию и локальные изображения. Готовый `index.html` можно открыть двойным кликом (`file://`); для работы не требуется подключение к сети.

## wiki.qsp.org → PWA

PWA — вариант одностраничника, предназначенный для размещения на веб-сервере. Он строится из того же корпуса `.build/wiki` и включает возможности SPA, а также манифест, офлайн-кэширование и поиск.

### Шаг 1. Скачать wiki

Если исходники ещё не получены или требуется обновление, выполните [общие действия по загрузке](#общий-исходник-wiki):

```bash
python -m qsp_help_builder download
```

### Шаг 2. Собрать PWA

```bash
python -m qsp_help_builder pwa
```

По умолчанию результат создаётся в:

```text
docs/
```

Каталог задаётся параметром `[pwa].out`, параметры манифеста — в секции `[pwa]` файла `qsp_help.toml`.

В выходной каталог входят:

- `index.html` — приложение;
- `manifest.webmanifest` — описание устанавливаемого приложения;
- `sw.js` — Service Worker, который кэширует сборку для офлайн-работы после первого посещения;
- `search.json` — индекс клиентского полнотекстового поиска;
- CSS и `images/`.

### Шаг 3. Опубликовать на GitHub Pages

1. Соберите PWA командой `python -m qsp_help_builder pwa`.
2. Добавьте каталог `docs/` в Git и закоммитьте его.
3. В настройках репозитория откройте **Settings → Pages**.
4. Выберите **Deploy from a branch**, нужную ветку и каталог `docs`.
5. Дождитесь публикации сайта.

Сайт будет доступен в подкаталоге вида `https://<user>.github.io/<repo>/`. Относительные пути сборки учитывают этот вариант размещения.

Первое посещение должно быть по HTTPS: Service Worker не работает с `file://`. После первого посещения PWA становится доступна офлайн и может быть установлена как приложение.

### Обновление опубликованной версии

Для повторной публикации достаточно:

1. пересобрать `pwa`;
2. закоммитить обновлённый `docs/`.

Service Worker меняет имя кэша по содержимому сборки, поэтому браузер подтянет обновлённую версию без ручной очистки кэша.

## wiki.qsp.org → Docusaurus

Этот сценарий преобразует скачанный wiki-корпус в дерево Markdown-файлов, которое можно использовать как `docs.path` в проекте Docusaurus.

### Шаг 1. Скачать wiki

Если `.build/wiki` ещё не подготовлен или его нужно обновить, выполните [общие действия по загрузке](#общий-исходник-wiki):

```bash
python -m qsp_help_builder download
```

### Шаг 2. Собрать дерево Markdown

```bash
python -m qsp_help_builder docusaurus
```

По умолчанию результат находится в:

```text
.build/docusaurus_docs/
```

Каталог задаётся параметром `[docusaurus].out`; slug корневой страницы — `[docusaurus].start_page`.

Сборщик извлекает структуру содержания wiki и создаёт вложенное дерево Markdown:

- страницы из содержания помещаются в `qsp_wiki/`, вложенность соответствует уровням TOC;
- страницы вне содержания и служебные материалы (например, `help_keywords`) помещаются в `help_add/`;
- для папок создаются `_category_.json`;
- порядок страниц задаётся через `sidebar_position`, при необходимости используется `sidebar_label`;
- отдельный `sidebars.js` не требуется — Docusaurus строит sidebar по метаданным.

### Картинки

Картинки копируются рядом с документами, которые их используют. Отдельный общий каталог изображений не создаётся, поскольку Docusaurus иначе может превратить его в отдельный раздел. Дубликаты одной картинки в разных папках допустимы.

### Сохранение порядка и ссылок

Для сохранения номеров страниц и целей ссылок между пересборками используются JSON-базы из `[docusaurus].bases` (по умолчанию `.build/docusaurus_docs/.docusaurus_build`):

- `numbering.json`;
- `links.json`.

**Не удаляйте и не переносите эти базы.** При перемещении документа база хранит прежний адрес. Ручные изменения номеров в `_category_.json` или `sidebar_position` будут перезаписаны при следующей сборке.

Сборка заново создаёт дерево Markdown (старые `.md`/`.mdx` и папки удаляются), но сохраняет базы. Поэтому перемещение раздела не оставляет устаревших копий страниц.

## Docusaurus Markdown → CHM

Этот конвейер использует Markdown-источники Docusaurus, а не HTML-корпус `.build/wiki`. Он изолирован от wiki-сборок и не изменяет `.build/wiki`, `.build/chm`, `.build/spa` или опубликованный `docs/`.

### Шаг 1. Синхронизировать Markdown-исходники

```bash
python -m qsp_help_builder markdown-sync
```

Команда использует Git sparse checkout по настройкам `[docusaurus_markdown]` из `qsp_help.toml`. Исходники синхронизируются в:

```text
.build/docusaurus_source/
```

Синхронизация сообщает commit SHA исходного репозитория. Для неё требуется установленный Git.

### Шаг 2. Проверить Markdown

```bash
python -m qsp_help_builder markdown-validate
```

Проверка выполняется локально, без сети, и не изменяет выходные каталоги. Проверяются:

- front matter;
- поддерживаемая Markdown-разметка;
- явные anchors;
- относительные ссылки и fragments;
- локальные изображения;
- соответствие набора страниц `docusaurus_markdown/toc.json`.

Raw HTML, MDX, admonitions, setext-заголовки, H5/H6 и неизвестные языки code fence не поддерживаются. Ошибки указываются с файлом и строкой. В текущем наборе предусмотрено 62 Markdown-страницы из `qsp_wiki/` и `help_add/`.

### Шаг 3. Собрать CHM

```bash
python -m qsp_help_builder markdown-build --target chm
```

Результат:

```text
.build/docusaurus_markdown/chm/
```

В каталоге создаются HTML-страницы, `qsp.hhc`, `qsp.hhk`, CSS и изображения.

Пути выхода и state-манифесты задаются параметрами `chm_out` и `state` секции `[docusaurus_markdown]`.

При повторном запуске неизменённая цель пропускается. Сборка выполняется в staging-каталоге и заменяет текущий результат только после успеха; при ошибке предыдущая сборка и её манифест сохраняются.

> В этом сценарии подготовленные CHM-файлы также необходимо компилировать внешним HTML Help Workshop — как в [wiki.qsp.org → CHM, шаг 4](#шаг-4-скомпилировать-chm).

## Docusaurus Markdown → SPA

Сценарий собирает автономный одностраничник из Markdown-источников Docusaurus.

### Шаг 1. Синхронизировать исходники

Выполните [синхронизацию Markdown](#шаг-1-синхронизировать-markdown-исходники) из раздела **Docusaurus Markdown → CHM**:

```bash
python -m qsp_help_builder markdown-sync
```

### Шаг 2. Проверить исходники

Выполните [проверку Markdown](#шаг-2-проверить-markdown) из раздела **Docusaurus Markdown → CHM**:

```bash
python -m qsp_help_builder markdown-validate
```

### Шаг 3. Собрать SPA

```bash
python -m qsp_help_builder markdown-build --target spa
```

Результат:

```text
.build/docusaurus_markdown/spa/
```

В каталоге будут `index.html`, CSS и `images/`.

Параметр выходного каталога — `spa_out` в `[docusaurus_markdown]`. Как и остальные Markdown-сборки, результат создаётся через staging и заменяет прежний каталог только после успешной сборки.

## Сборка всех Markdown-целей

Если нужно собрать все три формата из Markdown за один раз, после синхронизации и проверки выполните:

```bash
python -m qsp_help_builder markdown-build --target all
```

Команда создаёт CHM, SPA и PWA в отдельных каталогах:

| Цель | Каталог по умолчанию |
|---|---|
| CHM | `.build/docusaurus_markdown/chm/` |
| SPA | `.build/docusaurus_markdown/spa/` |
| PWA | `.build/docusaurus_markdown/pwa/` |

Пути задаются ключами `chm_out`, `spa_out`, `pwa_out` и `state` в `[docusaurus_markdown]`.

Для каждой цели сохраняется state-манифест. Неизменённые цели пропускаются, сборка выполняется через staging, а предыдущий результат сохраняется в случае ошибки рендеринга.

## Проверка и тесты

Регрессионные тесты проекта запускаются командой:

```bash
python -m pytest
```

Тесты охватывают модель сайта, профили выходных форматов, рендереры CHM/SPA/PWA/Docusaurus, загрузчик, обработку якорей, CLI и идемпотентность ссылок.

## Расположение файлов и сброс сборок

| Каталог | Назначение |
|---|---|
| `qsp_help_builder/` | Код сборщика |
| `assets/` | Статические ресурсы |
| `.build/` | Локальные рабочие данные и результаты; игнорируется Git |
| `.build/wiki/` | Скачанный wiki-корпус |
| `.build/chm/` | Подготовленные файлы wiki для CHM |
| `.build/spa/` | Wiki-SPA |
| `.build/docusaurus_docs/` | Markdown-дерево wiki для Docusaurus |
| `.build/docusaurus_source/` | Синхронизированные Markdown-исходники Docusaurus |
| `.build/docusaurus_markdown/` | Результаты CHM/SPA/PWA из Markdown |
| `docs/` | Публикуемый каталог wiki-PWA для GitHub Pages |

Локальные скачанные данные и обычные результаты можно восстановить повторным запуском соответствующих команд. Для сброса сохранённого порядка Docusaurus удалите `.build/docusaurus_docs/.docusaurus_build/` — это сбросит базы состояния Docusaurus. Не удаляйте эти базы, если хотите сохранить нумерацию и адреса ссылок между сборками.

Каталог `docs/` — исключение: это публикационный результат GitHub Pages, его необходимо коммитить после сборки PWA.

## Дополнительная информация

- Для wiki-цепочек `download` перезаписывает `.build/wiki` целиком. Зафиксированный baseline и проверки приёмки описаны в `_baseline/2026-10-17/BASELINE.md`; манифесты можно создавать через `python _baseline/make_manifest.py`. Старый baseline `_baseline/2026-10-16/` сохранён как история.
- Сборка Docusaurus Markdown использует `docusaurus_markdown/pages.json` для выбора файлов и сопоставления `source → slug`, а `docusaurus_markdown/toc.json` — для дерева навигации. В `pages.json` можно задавать директории или glob, исключения, уникальные slug и заглушки, исключённые из публикации. Набор selectors должен точно покрывать итоговый список выбранных Markdown-файлов.
- Все выбранные slug должны присутствовать в `toc.json` ровно один раз. Неизвестные, повторяющиеся или отсутствующие страницы вызывают ошибку проверки.
- Исключённые заглушки `help_qspider_standalone.md` и `glossary_snippet.md` перечислены в `unlinked_excluded`: ссылки на них становятся обычным текстом, а сами страницы не попадают в справку и TOC.
- Локальные картинки берутся из Markdown-ссылок и копируются в staging/source; внешние HTTP(S)-ссылки сохраняются. Ссылки на `.md`-страницы и fragments должны разрешаться строго.
- DokuWiki-генератора в проекте нет. Экспериментальный `docu_at_wiki/qspdocuwiki` использовался как внешний пример; исторические решения и ограничения описаны в `hist/project-context.md`.
